# 発展編: ループを本番に近づける4つの部品

本編で作ったループは1本でした。実務のループエンジニアリングでは、
さらに次の部品を組み合わせます。それぞれ「本編のループに残る痛み」に対応しています。

## 1. Worktrees — 並行するループの隔離

**残る痛み**: ループを2本同時に走らせると、同じ作業ディレクトリを取り合って壊れる。

git worktree はリポジトリの複数のブランチを別ディレクトリに同時にチェックアウトする
仕組みです。ループごとに専用の作業コピーを与えれば、並行実行しても衝突しません。
Claude Code ではサブエージェントに `isolation: worktree` を指定したり、
セッションを worktree 上で開始したりできます。

**試すヒント**: BACKLOG のタスクを2つ選び、worktree を2つ作ってそれぞれで
Step 4 のループを同時に走らせ、最後に2本のブランチをマージしてみる。

## 2. Skills — 知識のコード化

**残る痛み**: ループは毎周回、プロジェクトの約束事（コマンド、規約、地雷）をゼロから
推測し直している。推測はたまに外れる。

SKILL.md はプロジェクト固有の手順や判断基準を再利用可能な形で記述したファイルです。
「このプロジェクトのテストの流儀」「リリース手順」などを一度書けば、
どの周回・どのエージェントも同じ知識から始められます。
本編の SPEC.md が「何を作るか」の知識だったのに対し、Skill は「どう作業するか」の知識です。

**試すヒント**: 本編で reviewer が繰り返し指摘した内容を `.claude/skills/` の
スキルにまとめ、実装側が最初から守るようになるかを観察する。

## 3. スケジュール実行 — 人間なしの起動

**残る痛み**: `/loop` の起動だけは、まだ人間がやっている。

cron やスケジュールされたエージェント実行を使うと、「毎朝9時に CI の失敗と
バックログを triage して、直せるものは PR にする」のような**あなたが寝ている間の
ループ**が作れます。ここまで来ると、人間の接点は起動ではなく
**結果のトリアージ（受信箱）だけ**になります。

**試すヒント**: まずは1日1回、「BACKLOG と最近のテスト結果を読んで、今日やるべき
タスクの提案を書き出すだけ」の読み取り専用ループから始めると安全です。

## 4. MCP コネクタ — ループの入口と出口を現実につなぐ

**残る痛み**: BACKLOG.md は手書きです。仕事の発生源（Issue、障害通知、レビュー依頼）と
成果の届け先（PR、チケット、チャット）は、リポジトリの外にあります。

MCP（Model Context Protocol）のコネクタを使うと、ループが Issue トラッカーから直接
仕事を発見し、成果を PR やチケット更新として届けられるようになります。
BACKLOG.md はその第一歩の「手元で完結する代用品」だったと言えます。

**試すヒント**: BACKLOG.md の代わりに GitHub Issues を状態にして、
「ラベル `agent-ok` の付いた Issue を1つ選んで着手する」ループに置き換えてみる。
