# 発展編: ループを本番に近づける部品たち

本編で体験したのは、6つのプリミティブ（スケジューリング / Worktrees / Skills /
MCP / Sub-agents / Memory・State）のうち、検証ループ・外部状態・Sub-agents・
自動化の4つでした（詳しくは[概念解説](what-is-loop-engineering.md)）。
この発展編では残りのプリミティブと実行基盤を扱います。
それぞれ「本編のループに残る痛み」に対応しています。

## 1. Worktrees — 並行するループの隔離

**残る痛み**: ループを2本同時に走らせると、同じ作業ディレクトリを取り合って壊れる。

git worktree はリポジトリの複数のブランチを別ディレクトリに同時にチェックアウトする
仕組みです。ループごとに専用の作業コピーを与えれば、並行実行しても衝突しません。
Claude Code ではサブエージェントに `isolation: worktree` を指定したり、
セッションを worktree 上で開始したりできます。

**試すヒント**: BACKLOG のタスクを2つ選び、worktree を2つ作ってそれぞれで
Step 4 のループを同時に走らせ、最後に2本のブランチをマージしてみる。

## 2. Skills — 知識のコード化

**残る痛み**: ループは毎周回、プロジェクトの約束事（コマンド、規約、地雷）をゼロから
推測し直している。推測はたまに外れる。

SKILL.md はプロジェクト固有の手順や判断基準を再利用可能な形で記述したファイルです。
「このプロジェクトのテストの流儀」「リリース手順」などを一度書けば、
どの周回・どのエージェントも同じ知識から始められます。
本編の SPEC.md が「何を作るか」の知識だったのに対し、Skill は「どう作業するか」の知識です。

**試すヒント**: 本編で reviewer が繰り返し指摘した内容を `.claude/skills/` の
スキルにまとめ、実装側が最初から守るようになるかを観察する。

## 3. スケジュール実行 — 人間なしの起動

**残る痛み**: `/loop` の起動だけは、まだ人間がやっている。しかも `/loop` は
**セッションスコープ**なので、ターミナルを閉じればループも止まります
（放置しても7日で自動期限切れになる安全設計でもあります）。

Claude Code はスケジュール実行の手段を3つ提供しており、公式ドキュメント
（[Scheduled tasks](https://code.claude.com/docs/ja/scheduled-tasks)）が比較表を
まとめています。要点はこうです。

| 方式 | どこで動く | マシン起動 | セッション | 最小間隔 |
|------|----------|----------|----------|---------|
| `/loop`（本編 Step 4） | 手元 | 必要 | 必要 | 1分 |
| Desktop スケジュールタスク | 手元 | 必要 | 不要 | 1分 |
| Routines（クラウド） | Anthropic 管理環境 | **不要** | 不要 | 1時間 |

Routines はセッション内から **`/schedule` スラッシュコマンド**で作成・管理できます
（例: `/schedule 毎朝9時にバックログを読んで今日のタスク提案をまとめる`）。
ここまで行くと、「毎朝9時に CI の失敗とバックログを triage して、直せるものは
PR にする」のような**あなたが寝ている間のループ**が作れます。人間の接点は
起動ではなく**結果のトリアージ（受信箱）だけ**になります。

もうひとつ注目すべきは **`loop.md`** です。プロジェクトに `.claude/loop.md` を
置くと、引数なしの `/loop` が実行するデフォルトプロンプトをそれに差し替えられます。
つまり「このプロジェクトの定常ループが何をすべきか」を、プロンプトの打ち直しではなく
**リポジトリ内のファイルとして管理・改善**できるということです。外部状態（BACKLOG.md）が
「何をやるか」を持つのに対し、loop.md は「毎周どう回るか」を持つ——ループ自体の
コード化です。

**試すヒント**: ①本編の Step 4 で使ったループのプロンプトを `.claude/loop.md` に
保存し、引数なしの `/loop` だけで回るようにする。②スケジュール実行に進むときは、
まず1日1回「BACKLOG と最近のテスト結果を読んで、今日やるべきタスクの提案を
書き出すだけ」の読み取り専用ループ（L1）から始めると安全です。

## 4. MCP コネクタ — ループの入口と出口を現実につなぐ

**残る痛み**: BACKLOG.md は手書きです。仕事の発生源（Issue、障害通知、レビュー依頼）と
成果の届け先（PR、チケット、チャット）は、リポジトリの外にあります。

MCP（Model Context Protocol）のコネクタを使うと、ループが Issue トラッカーから直接
仕事を発見し、成果を PR やチケット更新として届けられるようになります。
BACKLOG.md はその第一歩の「手元で完結する代用品」だったと言えます。

**試すヒント**: BACKLOG.md の代わりに GitHub Issues を状態にして、
「ラベル `agent-ok` の付いた Issue を1つ選んで着手する」ループに置き換えてみる。

## 5. 実行基盤のバリエーション — /loop の外へ

**残る痛み**: `/loop` はセッションの中で生きている。ターミナルを閉じればループも死ぬ。

ループの本質は「起動→1周分の作業→記録」の繰り返しであって、`/loop` はその実行基盤の
ひとつにすぎません。基盤は要件に応じて選べます。

| 基盤 | 特徴 | 向いている用途 |
|------|------|--------------|
| シェルスクリプト＋ `claude -p` | 最も原始的。while ループで headless 実行を回すだけなので、仕組みが完全に見える。「Ralph ループ」として知られ、公式プラグインもある | ループの原理を理解する。CI に組み込む前の試作 |
| `/loop`（セッション内） | 手軽。ただしセッション終了で停止 | 本ハンズオンのような対話圏内の反復作業 |
| スケジュール実行（Routines / Desktop タスク） | 定期起動。Routines はクラウド実行で PC を閉じても回る | 毎朝のトリアージなど「あなたが寝ている間」のループ |
| CI 常駐（GitHub Actions 等） | イベント駆動＋cron。チームの既存パイプラインに同居できる | Issue 起票や CI 失敗をトリガーにするチームのループ |
| Agent SDK | コードでループを書く。フックで危険操作の拒否リストやトークン予算ガードを実装できる | 停止条件・権限制御を厳密に作り込む本番運用 |

どの基盤でも、本編で作った部品（検証可能なゴール・外部状態・検証の分離・停止条件）は
そのまま持ち運べます。**基盤が変わっても、設計するものは変わりません。**
