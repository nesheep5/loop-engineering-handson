# Phase 2: 消化ループ

この Phase であなたが作るもの: 消化ループのプロンプト（`.claude/loop.md`）、qa エージェント定義
ループが作るもの: `report` コマンドの実装・テスト・PR

## 1. なぜこの部品か

[本編 Step 4](../steps/step4.md) で回したフルループの実務版です。チケットという検証可能な
入力が Phase 1 で揃った今、そこに「PR という単位」と「1チケット=1ブランチ=1PR」の
粒度規律を加えて、消化ループを組み立てます。

## 2. 作る1: 消化ループのプロンプト

`.claude/loop.md` を自作します。引数なしの `/loop` はこのファイルをデフォルトプロンプトとして
実行する仕様です（[発展編](../advanced.md)で既習）。以下の構成要素チェックリストを
すべて満たしてください。

- [ ] チケットの選択基準（status: todo かつ priority 最小）と、無いときの終了条件
- [ ] status 遷移の更新（todo→in-progress→in-review）
- [ ] ブランチ運用（`feat/<チケットid>`、main から分岐、周回の最後に main へ戻る）
- [ ] 検証3点セット（test / lint / typecheck）の全通過
- [ ] PR 作成**前**のセルフレビュー（autoreview）の指示
- [ ] push と PR 作成（タイトルにチケット id、本文は PR テンプレートの4点）
- [ ] 1周1チケット、マージはしない（人間の仕事）

詰まったら [`docs/practical/answers.md`](answers.md) の3節（消化ループのプロンプト例）を
参照してください。

## 3. 作る2: qa エージェント定義

`.claude/agents/qa.md` を自作します。本編の reviewer が判断基準に SPEC.md を使っていたのに
対し、実践編ではチケットの受け入れ基準がその役割を引き継ぎます。以下のチェックリストを
すべて満たしてください。

- [ ] 判断基準はチケットの受け入れ基準**のみ**
- [ ] 受け入れ基準を実際にコマンド実行で検証する指示
- [ ] 報告形式（承認/差し戻し、基準ごとの実行結果、懸念）
- [ ] コードを変更しない・忖度しない指示

詰まったら [`docs/practical/answers.md`](answers.md) の2節（qa エージェント定義の例）を
参照してください。

## 4. 設計判断: qa はどこに置くか

qa をどこで起動するかには2つの選択肢があります。

- **ループ内（PR 作成前）に置く**: 差し戻しが速く周回内で完結しますが、検証が実装者側の
  ループに取り込まれるため独立性が下がります
- **PR 後の独立した検証にする**: 実装から切り離された立場で検証でき、人間のマージ判定の
  直前材料になりますが、差し戻しのたびに人間の介在が要ります

本手順では**PR 後**を採用します。検証の分離を「PR」という実務の単位で保つためです。
実装ループと検証を同じプロセスに同居させると、検証が「自分の作業を自分で丸める」形に
なりやすく、独立性が薄れます。PR という境界を挟むことで、qa は常に実装ループの外側から
チェックする立場を保てます。

## 5. 回す

`/loop` で `.claude/loop.md` を回します。観察ポイントは、周回ごとに PR が1本ずつ
増えることです。

## 6. 人間の判断（マージ判定）

PR ごとに、次の手順で判定します。

1. `gh pr list` で確認し、qa を起動する。プロンプト例:

   ```
   qa サブエージェントで PR #<番号> のブランチをチケット <id> の受け入れ基準で検証して
   ```

2. qa の報告と PR の「レビュアーに見てほしい箇所」を読む
3. 判定する。承認なら `gh pr merge <番号> --squash --delete-branch`、差し戻しなら PR に
   コメントを書きループに修正させる
4. **気づきを部品に反映する（フィードバックループ）** — 承認・差し戻しのどちらでも、
   レビューで気づいたことがあれば1行で Claude に伝え、埋め込み先を判断させて追記・
   コミットさせます。プロンプト例:

   ```
   この気づきを次の周回から効くように適切な部品に追記して。コミットメッセージは
   「改善: 」で始めて — <気づきの内容>
   ```

   埋め込み先の目安は次のとおりです。

   | 気づきの種類 | 埋め込み先 |
   |------|------|
   | 実装時の観点（書き方・進め方） | loop.md のセルフレビューの観点 |
   | PR レビュー時の観点（検証・品質） | qa の追加の検証観点 |
   | チケットの切り方 | planner |
   | プロジェクト全体の規約 | CLAUDE.md |

   この一手間が、消化ループを「回すたびに同じ指摘を繰り返す」状態から
   「回すたびに賢くなる」状態に変えます。気づきをその場限りの発言で終わらせず、
   ファイルに定着させることが、消化ループ自体をフィードバックループにします。

5. マージ後、チケットの status を done に更新して push します（Claude に頼んで良い）
6. 次の PR へ。全 Story が done になるまで繰り返します。**後の周回ほど自分の指摘が
   減っていくか**を観察してください

ステータスの定義は [`tickets/README.md`](../../tickets/README.md) を参照してください。

## 7. チェックポイント

- あなたがこの Phase で書いたのはループの部品だけで、プロダクトのコードは1行も
  書いていません。それでも全 PR の内容を説明できますか。できないなら、qa と PR
  テンプレートのどこを強化するべきでしょうか
- `git log --oneline | grep 改善:` で、あなたのレビュー観点が何件ループに蓄積された
  かを数えてください。それらは次の周回で本当に効いたでしょうか
