# Phase 3: 出口とループ改善

この Phase であなたが作るもの: ループの改善1件
CI が作るもの: 公開された月次レポート

## 1. なぜこの部品か

Phase 2 でチケットは着々と done になり、PR も積み上がりました。しかし
「マージしたら終わり」ではありません。マージは main への push を意味し、
それを契機に CI が動きます。この Phase では、まず CI が実際に何をしているかを
確認し、次に Phase 2 で積み残した「フィードバックループの振り返り」に
決着をつけます。ループを1周走らせるだけでなく、**ループの構造そのものを
改善する**のがこの Phase の主題です。

## 2. デプロイを確認する

1. [`.github/workflows/deploy-report.yml`](../../.github/workflows/deploy-report.yml) を開き、
   何をしているか読んでください。おおまかな流れは次のとおりです。

   - `report` コマンドの出力をチェックする（`npm run kakeibo -- report` の
     標準出力に HTML が含まれるかを試す）
   - HTML が含まれていればレポートを生成する
   - 生成したレポートを GitHub Pages へデプロイする

   **`report` が HTML を出力するようになるまではデプロイをスキップする**
   ガードが入っている点に注目してください。Phase 2 の早い周回ではまだ
   `report` が実装されておらず、このワークフローは「何もせず成功する」状態の
   まま何度か走っていたはずです。Phase 2 が完了して初めて、このガードを
   通過してデプロイが実行されます。

2. GitHub 上の fork リポジトリで Actions タブを開き、最後のマージ（main への push）
   に対応するワークフロー実行を確認してください。ビルドとデプロイの両方の
   ジョブが緑になっているはずです。

3. `https://<あなたのアカウント>.github.io/<リポジトリ名>/` を開き、
   公開された月次レポートを確認してください。

4. 動作しないときは、次の3箇所を順に確認してください。

   - fork リポジトリの Settings → Pages → Source が「GitHub Actions」に
     なっているか（実践編セットアップの手順4）
   - `report` コマンドの出力（ローカルで
     `npm run --silent kakeibo -- report 2026-07` を実行し、標準出力に
     `<html` を含む HTML が出るか。CI のガードはこの内容で判定します）
   - Actions のログ（`check` ステップが `has-report=false` を出していないか、
     デプロイジョブがそもそもスキップされていないか）

## 3. メタ改善: フィードバックループの振り返りと昇華

Phase 2 では、PR ごとの気づきをその都度「改善:」コミットで部品に反映してきました。
これは1件ずつは小さな改善でも、蓄積を俯瞰すると別の見え方をすることがあります。

まず次のコマンドで、これまでの改善コミットを眺めてください。

```bash
git log --oneline | grep 改善:
```

Phase 2 のフィードバックループは「実装時の観点」「検証観点」「チケットの
切り方」「プロジェクト全体の規約」という4つの埋め込み先を用意していましたが、
毎回その場の指摘を最短距離で埋め込むことに追われ、**もっと上流の気づき**を
反映しきれずに素通りしていないでしょうか。たとえば次のようなものです。

- **planner の指示文**（例: あるチケットの受け入れ基準が曖昧で、qa の判定に
  迷いが生じた → 「期待結果はコマンドと出力で書く」という指示を追加する）
- **チケットの切り方そのもの**（例: 特定の Story が明らかに大きすぎて1周で
  終わらなかった → 「良いチケットの4条件」のうち大きさの目安を、より具体的な
  基準に書き直す）
- **CLAUDE.md**（例: 複数の PR で似た指摘を繰り返していた → その観点は
  個別の部品ではなく、プロジェクト共通の規約として CLAUDE.md に昇華する）

この3つはあくまで例です。あなた自身の `git log` の蓄積から、**反映しきれて
いなかった上流の気づきを1つ選んで**改善してください。Phase 2 の改善が
「1回の指摘を1箇所に埋め込む」局所修正だったのに対し、ここでの改善は
「積み重なった指摘のパターンを読み、構造そのものを直す」メタ改善です。
コミットメッセージは Phase 2 と同じく「改善:」で始めてください。

反映したら、可能であれば `workflow_dispatch` などで実際に動かして確認できる
範囲は動かし、改善が効いているかを観察してください（たとえば planner の
指示を直したなら、次にチケットを起票させたときに受け入れ基準の書き方が
変わっているか、といった具合です）。

## 4. 振り返り: 砂時計

実践編全体を通して、あなたとループがそれぞれ何を担ったかを図にすると、
次の「砂時計」の形になります。

```
人間:  PRD・チケットの採否・優先順位     (入口)
         ↓
機械:  実装 → 検証 → autoreview → PR    (中間: 自動化された消化・検証)
         ↓
人間:  QA 報告を読んでマージ判定         (出口)

人間:  ループ自体の設計と改善            (外側から全体を包む)
```

入口と出口を人間が締め、中間の太い部分を機械が消化する。そして、その砂時計
全体を「ループ自体の設計と改善」という人間の仕事が外側から包んでいます。
この形を踏まえて、次の問いに答えてください。

- この実践編であなたが判断した箇所を列挙せよ（PRD、採否、優先順位、
  マージ判定×枚数、改善1件——それ以外に何かあったか？）
- その判断は、チーム開発で PdM / Eng / QA の誰の仕事だったか？

## 5. おわりに

実務への持ち込みは、本編 [Step 4](../basic/step4.md) が示した段階的自律
**L1（報告のみ）**から始めるのが定石です。この実践編で組んだ構造は、
入口と出口をそのままに、中間の実装だけを実プロジェクトの道具に差し替えれば
実務に移行できます。たとえば、チケットの起票元である JIRA モック
（`tickets/` ディレクトリ）を実際の JIRA と MCP 連携に置き換え、
`gh pr merge` による即時マージをブランチ保護と必須レビュー承認フローに
置き換えれば、入口（要件と優先順位）・中間（実装ループ）・出口
（マージ判定）・外側（改善の反映）という同じ骨格のまま、実務のチームに
持ち込めます。最初は L1 でループにレポートだけを書かせ、判定の精度に
確信が持てるようになってから、段階的に権限を広げてください。

これで実践編は完走です。本編に戻るときは [README](../../README.md) を、
さらに Worktrees・Skills・スケジュール実行・MCP を学ぶときは
[発展編](../advanced.md) を参照してください。
