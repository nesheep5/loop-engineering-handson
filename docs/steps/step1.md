# Step 1: 検証ループ — ゴールと検証手段を渡す（35分）

## Step 0 の痛み

あなたは「実行して結果を貼る係」でした。Claude の修正能力に問題はなく、
**検証手段を持たされていなかった**だけです。

## コンセプト: プロンプトではなくループを渡す

ループエンジニアリングの最小単位は次の形です。

```
ゴール（検証可能な終了条件） ＋ 検証コマンド ＋ 「通るまで続けよ」
```

エージェントは 修正 → 実行 → 観察 → 修正 のループを自分で回せます。
人間の仕事は個々の指示ではなく、**ループの終了条件を設計すること**に変わります。

良いゴールの条件:

- **機械が判定できる**（`npm test` の成功/失敗。「いい感じにして」は不可）
- **エージェント自身が検証を実行できる**（人間の目視が必要な条件はループを止める）
- **二値である**（達成したか、していないか）

もうひとつ、ゴールとセットで設計すべきものが**停止条件**です。
ループは「終了条件を満たすまで回る」仕組みなので、満たせないゴールを渡すと
永遠に回り続けます（時間とトークンを燃やしながら）。実務では
「試行は最大N回まで」「予算・時間の上限」「同じ失敗をK回繰り返したら人間に報告して停止」
のような打ち切りを、ループを回し始める**前**に決めておきます。

## 演習: 検証ループを渡す（20分）

新しいセッション（`/clear` 推奨）で、今度はこう頼みます。

```
app ディレクトリで npm test / npm run lint / npm run typecheck を実行し、
すべて成功する状態にしてください。
修正のたびに自分でコマンドを実行して確認し、全部通るまで続けてください。
仕様の判断に迷ったらリポジトリルートの SPEC.md に従ってください。
最後に、3つのコマンドの実行結果を証拠として貼って報告してください。
```

最後の一文は**証拠主義**です。「できました」という自己申告ではなく、実行した
コマンドと出力を提出させます。証拠を眺める方が、自分で再検証するより速く、
あなたが見ていなかった実行に対しても機能します。

今回はあなたはコマンドを1回も実行しません。**眺めているだけ**です。

### 観察ポイント

- Claude が自分でテストを実行し、失敗を読み、修正し、再実行する様子
- lint エラー（デバッグ用 `console.log`、未使用 import、`any`）も自分で見つけて直すか
- 「月末の支出が抜ける」バグの原因（`summary.ts` の日付範囲）にたどり着くまでの過程

完了したら、あなたが最後に一度だけ検証してください（信頼はしても検証はする）:

```bash
cd app && npm test && npm run lint && npm run typecheck
```

問題なければ、修正をコミットさせておきましょう。以降のステップは毎回新しい
セッションで始めるため、未コミットの変更が残っていると次のエージェントが
「身に覚えのない差分」に混乱することがあります。

```
今回の修正を1つのコミットにまとめてコミットしてください。
```
