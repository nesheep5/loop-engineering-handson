# Step 2: 外部状態 — ループの記憶をファイルに置く（35分）

## 痛みの体験（5分）

Step 1 を終えたセッションで `/clear` を実行してから、こう聞いてみてください。

```
さっきの続きをやってください。
```

Claude は「さっき」を知りません。モデルは実行と実行の間に**記憶を持たない**からです。
毎回あなたが文脈を説明し直すなら、それはまた「人間が係をやる」状態に逆戻りです。

## コンセプト: 状態はモデルの外に置く

ループを何周も回すには、進捗がセッションをまたいで生き残る必要があります。
解決策は単純で、**状態をリポジトリ内のファイルに置き、ループの各周回に読み書きさせる**ことです。

このリポジトリでは `BACKLOG.md` がその外部状態です。開いて確認してください。

- タスクの一覧と優先順位（＝ループが発見する「仕事」）
- 運用ルール（＝1周分の作業量と完了条件の定義）
- 完了記録（＝次の周回への引き継ぎ）

ポイントは、プロンプトが**冪等**になることです。「BACKLOG から次のタスクをやれ」という
同じプロンプトを何度打っても、状態ファイルが進捗を教えてくれるので文脈が壊れません。

## 演習: 仕事を発見させる（25分）

`/clear` した新しいセッションで、こう頼みます。

```
BACKLOG.md を読んで、最優先の未完了タスクを1つだけ選んで実装してください。
完了条件と作業ルールは BACKLOG.md の運用ルールに従ってください。
完了したら BACKLOG.md に完了を記録してください。
```

最優先タスクは「format.ts のテスト追加」のはずです。観察ポイント:

- あなたはタスクの内容を**一言も説明していない**のに、正しい仕事が始まる
- 完了後、`BACKLOG.md` にチェックと完了メモが記録される

終わったらもう一度 `/clear` し、**まったく同じプロンプト**の前半だけを変えて聞いてみます。

```
BACKLOG.md を読んで、次にやるべき最優先の未完了タスクが何か教えてください。
まだ実装はしないでください。
```

前回の完了が記録されているため、Claude は正しく「次のタスク」（delete コマンド）を
指せるはずです。**記憶はセッションではなくファイルが持っている**ことを確認できました。

> delete コマンドの実装はここで止めてください。Step 3 の題材に使います。

## チェックポイント

1. あなたのプロンプトから「作業内容の説明」が消えました。代わりにどこへ移りましたか？
2. BACKLOG.md の運用ルールのうち、「1回の実行で1タスクだけ」という制約はなぜ重要だと思いますか？
   （ヒント: 1周が小さいほど、失敗したときに捨てられる量も小さい）
3. 外部状態が壊れる（例: 完了していないのに `[x]` が付く）と、ループはどうなりますか?

> 仕事の発見と記録は自動化できました。しかし今の完了判定は
> **実装した本人の自己申告**です。それを信じていいのでしょうか。
