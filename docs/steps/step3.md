# Step 3: 検証の分離 — 作った本人に採点させない（35分）

## 痛みの体験（15分）

`/clear` した新しいセッションで、**あえて仕様書に触れずに**こう頼んでください。

```
kakeibo に delete コマンドを実装してください。
ID を指定して支出を削除できれば OK の簡単なタスクです。
実装できたらテストも書いて、最後に自分でレビューして問題ないか報告してください。
```

多くの場合、Claude は配列からレコードを取り除く**物理削除**で実装し、テストも通し、
自己レビューでも「問題ありません。完了です」と報告します。

ここで `SPEC.md` の削除仕様を開いてください。

> 削除は**物理削除ではなく論理削除**とする。レコードは JSON から取り除かず、`deleted: true` を付与する

実装は「動く」し、テストも「通る」。しかし**仕様違反**です。
自己レビューがそれを見抜けなかったのは能力不足ではありません。実装した本人は、
自分の解釈（物理削除でよい）を前提にレビューするため、**解釈そのものの誤りを検出できない**のです。

> もし Claude が最初から SPEC.md を読み論理削除で正しく実装した場合も、そのまま進んで
> ください。次の reviewer レビューで「自己レビューとの厳しさの差」を観察できます。

## コンセプト: 検証を独立させる

ループエンジニアリングでは、**作るエージェントと検証するエージェントを分離**します。
検証側は別のコンテキスト・別の指示で動くため、実装者の思い込みを引き継ぎません。

このリポジトリには `.claude/agents/reviewer.md` として、
**SPEC.md だけを判断基準とし、コードを変更しないレビュアー**が定義済みです。

## 演習: reviewer に差し戻させる（15分）

同じセッションで続けてこう頼みます。

```
reviewer サブエージェントを使って、いまの delete コマンドの実装を
レビューしてください。
```

観察ポイント:

- reviewer が SPEC.md を引用して**差し戻し**を出すこと（物理削除・エラー処理漏れなど）
- 差し戻しを受けて実装側が修正し、再レビューで**承認**になるまでの流れ

承認が出たら、BACKLOG.md の delete タスクに完了を記録させてください。
最後にあなた自身でも確認します。

```bash
cd app && npm test && npm run lint && npm run typecheck
npm run kakeibo -- list        # 削除したはずのレコードが集計から消えているか
cat app/data/expenses.json     # レコード自体は残り deleted: true が付いているか
```

## チェックポイント

1. 自己レビューと reviewer のレビューで、指摘の質はどう違いましたか？
2. reviewer の強さの源泉はどこにあると思いますか？
   （ヒント: モデルの賢さではなく、**SPEC.md という独立した判断基準**と**別コンテキスト**）
3. 逆に、SPEC.md が曖昧だったら reviewer は機能するでしょうか？
   仕様を書くのは誰の仕事ですか？
