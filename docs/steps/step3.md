# Step 3: 検証の分離 — 作った本人に採点させない（35分）

## 痛みの体験（15分）

`/clear` した新しいセッションで、**あえて仕様書に触れず、しかも誤った実装方針まで
指定して**こう頼んでください。

```
kakeibo に delete コマンドを実装してください。
ID を指定したら app/data/expenses.json の配列から該当レコードを取り除く、
それだけの簡単なタスクです。
実装できたらテストも書いて、最後に自分でレビューして問題ないか報告してください。
```

実はこの依頼は [`SPEC.md`](../../SPEC.md) の削除仕様と矛盾しています。

> 削除は**物理削除ではなく論理削除**とする。レコードは JSON から取り除かず、`deleted: true` を付与する

依頼者が実装方針まで指定し、しかもそれが仕様違反——実務で日常的に起きる状況です。
ここから先は2つの分岐があり、**どちらに転んでも学びが成立します**。

### 分岐A: 指示どおり物理削除で実装した場合

Claude は配列からレコードを取り除き、テストも通し、自己レビューでも
「問題ありません。完了です」と報告するでしょう。実装は「動く」しテストも「通る」、
しかし仕様違反です。自己レビューがそれを見抜けないのは能力不足ではありません。
実装者は自分が受けた指示（物理削除でよい）を前提に採点するため、
**前提そのものの誤りを検出できない**のです。

### 分岐B: SPEC.md に気づき、指示を覆して論理削除で実装した場合

入念なエージェントは、依頼に書かれていなくても SPEC.md を自分で読み、
「依頼と仕様が矛盾していたので仕様に従いました」と報告することがあります。
このリポジトリのように仕様書が目立つ場所にあり「唯一の判断基準」と宣言されて
いる場合は、その可能性がかなり高くなります。

これも重要な観察です。エージェントが正しく振る舞えたのは、**仕様がリポジトリの
構造に組み込まれていたから**です。実プロジェクトでは仕様が Wiki の奥や誰かの
頭の中にあり、エージェントには読めません。そして「たまたま読んでくれた」に
頼るのは設計ではありません。次に導入する reviewer は、運に任せず
**毎回・構造的に**仕様と照合します。

## コンセプト: 検証を独立させる

ループエンジニアリングでは、**作るエージェントと検証するエージェントを分離**します。
検証側は別のコンテキスト・別の指示で動くため、実装者の思い込みを引き継ぎません。

このリポジトリには [`.claude/agents/reviewer.md`](../../.claude/agents/reviewer.md) として、
**SPEC.md だけを判断基準とし、コードを変更しないレビュアー**が定義済みです。

### もうひとつの罠: 検証の芝居（Verifier Theater）

「解釈違い」より悪質な失敗モードもあります。テストが通らないとき、エージェントが
**テストの期待値の方をバグに合わせて書き換え**、「全部通りました」と報告するケースです。
検証ループの信頼性は検証手段の信頼性に依存するので、検証手段そのものが
改ざんされると、ループ全体が「通ったふり」の芝居になります。

対策はプロンプトで「テストを書き換えるな」と祈ることではなく、**構造**で担保することです。
[`reviewer.md`](../../.claude/agents/reviewer.md) の frontmatter を開いて `tools:` の行を確認してください。
Read / Grep / Glob / Bash だけで、**Edit / Write を持っていません**。
レビュアーは物理的にコードもテストも書き換えられない——この権限分離が、
「検証者は改ざんに加担できない」ことの構造的な保証になります。

## 演習: reviewer に差し戻させる（15分）

同じセッションで続けてこう頼みます。

```
reviewer サブエージェントを使って、いまの delete コマンドの実装を
レビューしてください。
```

観察ポイント:

- 分岐Aなら、reviewer が SPEC.md を引用して**差し戻し**を出すこと（物理削除・エラー処理漏れなど）。
  差し戻しを受けて実装側が修正し、再レビューで**承認**になるまでの流れ
- 分岐Bなら**承認**になるはずですが、reviewer が自分でテストを実行し、SPEC.md の
  該当箇所と突き合わせた**証拠付きの判定**を出すことを確認してください。
  実装者の「問題ありません」という自己申告とは独立に、同じ厳格さの検証が
  毎回走る——これが構造の価値です

承認が出たら、[`BACKLOG.md`](../../BACKLOG.md) の delete タスクに完了を記録させてください。
最後にあなた自身でも確認します。

```bash
cd app && npm test && npm run lint && npm run typecheck
npm run kakeibo -- list        # 削除したはずのレコードが集計から消えているか
cat app/data/expenses.json     # レコード自体は残り deleted: true が付いているか
```

## チェックポイント

1. あなたのエージェントは分岐A・Bどちらでしたか？ その結果は何に依存していたと
   思いますか？（モデルの入念さ・仕様書の置き場所・指示の書き方）
2. reviewer の強さの源泉はどこにあると思いますか？
   （ヒント: モデルの賢さではなく、**SPEC.md という独立した判断基準**と**別コンテキスト**）

   仕様を書くのは誰の仕事ですか？
4. もし実装側がテストを改ざんして「通した」場合、いまの reviewer はそれを
   検出できるでしょうか？ 検出の根拠は何ですか？（ヒント: SPEC.md とテストの照合）
