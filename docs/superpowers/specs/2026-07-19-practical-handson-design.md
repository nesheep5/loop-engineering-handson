# 実践編ハンズオン 設計書

作成日: 2026-07-19

## 背景と目的

本編(Step 0〜4)はループの構成要素を砂場(kakeibo)で体験する教材だった。
実践編は、それを**実務の開発フロー**(開発要件→チケット化→実装→PRレビュー→マージ→CIデプロイ)に
写像する教材である。PdM / Eng / QA の3ロールが関わる「大きめの機能追加」を題材に、
**チケット作成ループ**と**消化ループ**の2本を学習者自身が組み立てる。

- **対象者**: 本編を完走したエンジニア(検証ループ・外部状態・reviewer・/loop を理解済み)
- **フォーカス**: 痛み体験は本編で完了済みとして置かない。**「誰が・何を・どのように作るか」**の
  構築フォーカスに徹する
- **公開ポリシー**: 本編と同じ。個人情報・実在の会社情報・ローカルパスを含めない。サンプルはすべて架空

## 決定事項(ブレインストーミングでの確定)

| 論点 | 決定 |
|------|------|
| ロール配分 | 学習者1人が PdM / Eng / QA を交代で演じる |
| チケット管理 | ローカルの JIRA 風モック(`tickets/` ディレクトリ + frontmatter)。実 JIRA は使わない |
| 題材アプリ | kakeibo を継続して拡張 |
| CI デプロイ | fork 前提。merge → GitHub Actions → GitHub Pages に月次レポートを自動公開 |
| 本編との接続 | 本編完走を前提知識とし、作業はクリーンな main を fork して開始 |
| 構成アプローチ | 入れ子ループ型(ロールごとに「そのロールのループ」を組み立てる) |

## 中核: 「誰が・何を・どのように作るか」マトリクス

作り手は3者。**教材**(fork 時点で存在)、**学習者=人間**(ループの部品を作る)、
**ループ=エージェント**(プロダクトを作る)。

| 成果物 | 誰が作る | どのように |
|--------|---------|-----------|
| 手順書・PRD テンプレ・tickets/ スキーマ・CI ワークフロー・PR テンプレ | 教材(同梱) | fork で入手。読んで理解する対象 |
| PRD「月次レポート機能」 | 学習者(PdM) | テンプレートに記入(Phase 1) |
| planner エージェント定義 | 学習者(PdM) | 「良いチケットの4条件」チェックリストに沿って自作(Phase 1) |
| チケット群 `tickets/*.md` | チケット作成ループ | planner が PRD から分解・起票。学習者は採否・優先順位の判定のみ |
| 消化ループのプロンプト(`.claude/loop.md`) | 学習者(Eng) | 構成要素(取得→ブランチ→実装→検証→autoreview→PR)から組み立て(Phase 2) |
| qa エージェント定義 | 学習者(QA) | 受け入れ基準ベースの検証手順を記述(Phase 2) |
| `report` コマンドの実装・テスト・PR | 消化ループ | 1チケット=1ブランチ=1PR で周回。学習者はマージ判定のみ |
| 公開される月次レポート | CI | merge を契機に自動デプロイ |
| ループの改善(規約追加・skill 化) | 学習者 | Phase 3 で失敗を1つ選びシステムに埋め込む |

**核心のメッセージ**: 学習者はプロダクトのコードを1行も書かない。学習者が作るのは
ループの部品(PRD・エージェント定義・ループプロンプト)だけで、プロダクト(チケット・
コード・PR・デプロイ)はすべてループが作る。これが「プロンプトを打つ仕事から
ループを設計する仕事へ」の実務形である。

教材への反映: overview.md にこのマトリクスを地図として掲載し、各 Phase 冒頭に
「この Phase であなたが作るもの / ループが作るもの」の2行を必ず置く。手順書の各節は
「作るもの→どのように→できたことの確認」の順で書く。

## 題材 Epic: 月次レポート機能

kakeibo に `report <YYYY-MM>` コマンドを追加し、月次レポートを HTML で生成する。
内容はカテゴリ別集計・予算対比(超過ハイライト)・前月比・上位カテゴリなど。

選定理由:
- Story 4〜5枚に自然に分解できる大きさで、消化ループが実際に複数周回る
- 生成物の HTML がそのまま GitHub Pages のデプロイ成果物になり、
  「機能追加→マージ→デプロイで URL に現れる」が一本の線でつながる

## JIRA モック: `tickets/` ディレクトリ

JIRA の本質概念だけを Markdown で再現する。専用ツールは作らない(YAGNI)。

- 1チケット=1ファイル(例: `tickets/EPIC-1.md`, `tickets/KAKEI-101.md`)
- frontmatter: `id` / `type`(epic|story) / `status`(todo|in-progress|in-review|done) /
  `priority` / `epic`(親) / 本文に受け入れ基準
- ステータス遷移はループが frontmatter を書き換えて表現(BACKLOG.md のチェックボックスの進化形)
- 受け入れ基準が QA ループの判断基準になる(本編の SPEC.md の役割を、実務では
  チケットの受け入れ基準が担うという対応を明示する)
- 開始時の `tickets/` は README のみ。中身は Phase 1 のループが埋める

## Phase 構成

各 Phase の型は「作る部品の一覧 → 組み立て → 回す → 観察」。

### Phase 1: チケット作成ループを組み立てる(PdM の帽子)

- 学習者が作る: PRD(テンプレートに記入)、`.claude/agents/planner.md`
- ループが作る: `tickets/*.md` のドラフト(受け入れ基準付き Story 分解)
- 人間の判断: 採否・優先順位・受け入れ基準の妥当性を判定し status を todo に確定
- 学び: planner の指示文に「良いチケットの4条件」(機械検証可能な完了条件 /
  1コンテキストに収まる / 独立 / diff が小さい切り方)をどう埋め込むか。
  チケットのレビューはコードのレビューより桁違いに安い(入口の判断)

### Phase 2: 消化ループを組み立てる(Eng + QA の帽子)

- 学習者が作る: `.claude/loop.md`(消化ループのプロンプト)、`.claude/agents/qa.md`
- ループが作る: `report` コマンドの実装・テスト・PR(1チケット=1ブランチ=1PR)
- 人間の判断: QA レポートと diff の要点を読み、マージ判定のみ行う(`gh pr merge`)。
  Story の枚数だけ繰り返す
- 設計判断の演習: qa の検証をループ内(PR 作成前)に置くか、PR 後の独立ループにするか
- 学び: 1チケット=1PR の粒度規律、レビューを PR の後ろから前へ移す原則、
  AI レビューはセンサーで人間は判定(出口の判断)

### Phase 3: 出口をつなぎ、ループを改善する

- CI/Pages: merge → GitHub Actions(test→build→`kakeibo report`)→ Pages 公開を確認。
  ワークフローは同梱済みなので「読んで理解し、動作を確認する」パート
- メタ改善: 周回中の失敗・差し戻しを1つ選び、planner の指示文 / loop.md / CLAUDE.md の
  どこに埋め込めば再発しないかを判断して反映(ループのチューニングを1回実際にやる)
- 振り返り: 砂時計の図(入口=PRD と採否 / 中間=自動化された消化・検証 /
  出口=マージ判定 / 外側=ループ改善)で「自分が判断した箇所」を確認して終了

## 追加するファイル

```
docs/practical/
  overview.md              # 入口: マトリクス(地図)、fork・Pages・gh CLI セットアップ、付録にファイル構成
  phase1-planning-loop.md  # チケット作成ループの組み立て手順
  phase2-delivery-loop.md  # 消化ループの組み立て手順
  phase3-release.md        # CI/Pages 確認、メタ改善、振り返り
  prd-template.md          # PRD テンプレート+月次レポート機能での記入例
  answers.md               # 模範解答: planner/qa 定義例、loop.md 例、模範チケット分解
tickets/
  README.md                # チケットスキーマ仕様、ステータス遷移図
.github/
  workflows/ci.yml             # PR 向け: test / lint / typecheck
  workflows/deploy-report.yml  # main push: report 生成 → Pages 公開(report 未実装時は安全にスキップ)
  pull_request_template.md     # PR 契約4点セット(意図/動作証明/リスク/注目箇所)
```

設計判断:
- **planner / qa / loop.md は学習者が書く**(完成品は同梱しない)。それが「組み立てる」
  フォーカスの中身。模範例は answers.md に置く
- **CI ワークフローと PR テンプレートは同梱**。組み立ての主役ではなく「読んで理解する」
  対象なので、fork した瞬間から動く状態にする

## 既存ファイルの変更

- `README.md` — 本編の後に実践編への導線を1ブロック追加
- `docs/advanced.md` — 実践編への相互リンク(該当箇所のみ)
- `app/` は変更しない。`report` コマンドの実装は学習者のループの仕事として残す

## 教材自体の検証(作成時)

1. 既存検証の維持: `npm test` / `npm run lint` / `npm run typecheck` が通ること
2. ワークフロー yaml の構文検証(actionlint があれば使用)
3. 通しのドライラン: 手順書どおりに Phase 1→2 を実際に実行
   (PRD 記入例 → planner でチケット分解 → 消化ループ1周をPR 作成直前まで)し、
   手順書のコマンドが全部動くことを確認。Pages 公開は fork 環境依存のため、
   確認手順を overview.md に明記する形でカバー
4. 公開ポリシー確認(個人情報・実在の社名なし、サンプルは架空)
