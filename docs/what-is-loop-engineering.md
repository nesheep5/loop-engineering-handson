# ループエンジニアリングとは何か

ハンズオンの背景知識をまとめた読み物です（所要 約10分）。
手を動かす前でも後でも読めますが、Step 4 まで終えてから読み返すと解像度が上がります。

## 一言でいうと

**エージェントに個々のプロンプトを打つのをやめ、「エージェントにプロンプトを打つ仕組み（ループ）」を設計・運用する技術**です。

人間の役割が「指示を出す人」から「仕組みを設計し、結果を監督するエンジニア」へ移ります。

## 誕生の経緯

2026年6月、Google のエンジニアリングリーダーである Addy Osmani がエッセイ
[Loop Engineering: Designing loops that prompt coding agents](https://addyosmani.com/blog/loop-engineering/)
を公開しました（同月、[O'Reilly Radar にも転載](https://www.oreilly.com/radar/loop-engineering/)）。
同じ週に開発者 Peter Steinberger がその主張を一文に圧縮したことで、この実践に名前がつきました。

> You shouldn't be prompting coding agents anymore.
> You should be designing loops that prompt your agents.
>
> （もうエージェントにプロンプトを打つべきではない。エージェントにプロンプトを打つループを設計すべきだ）

重要なのは、これが「新発明」ではなく**命名**だったことです。コーディングエージェントを
使い込む開発者たちの間で既に生まれつつあった運用スタイルに名前と構造が与えられ、
一気に共有可能な「discipline（規律ある実践）」になりました。

実際、命名の約1年前から実践は収斂し始めていました。2025年7月には Geoffrey Huntley が
「bash の while ループでエージェントに PROMPT.md を食わせ続けるだけ」という過激な最小構成
（[Ralph Wiggum 技法](https://ghuntley.com/ralph/)）で実プロダクトが作れることを実証し、
同年9月には Simon Willison が[「エージェントとは、ゴールに向けてツールをループで回すもの」
という定義から loop の設計こそが新しいスキルだ](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/)と論じています。
Osmani のエッセイは、こうして各所で証明されつつあった実践に構造と名前を与えたものです。

## なぜ今か: 抽象度の階段

AI とのつきあい方は、レバレッジポイント（人間の工夫が効く場所）を上へ移しながら進化してきました。

| 世代 | 人間が磨くもの | 前提となるAIの能力 |
|------|--------------|------------------|
| プロンプトエンジニアリング | 1回の指示の書き方 | 1問1答 |
| コンテキストエンジニアリング | AIに見せる情報の設計（仕様、規約、コード） | 長いコンテキストの活用 |
| **ループエンジニアリング** | **仕事の発見〜検証〜記録が自律的に回る構造** | 長時間の自律動作と自己検証 |

エージェントが「数分間の対話相手」から「数時間動き続けるワーカー」になったとき、
ボトルネックは指示の質ではなく、**指示を出し続ける人間自身**になりました。
ループエンジニアリングはこのボトルネックを構造で解消します。

## ループの解剖学

### 最小単位: 検証ループ

すべての基礎は、エージェント自身が回せるこのサイクルです。

```
ゴール（検証可能な終了条件）
   ↓
行動 → 検証（テスト・lint・実行） → 差分を観察 → 修正 → …
   ↓
終了条件を満たしたら完了
```

ここで人間が設計するのは行動の中身ではなく、**終了条件と検証手段**です。
「いい感じにして」はループになりません。「`npm test` が全部通る」はループになります。

実践者の間では、ループエンジニアリングは高尚な概念というより
**停止条件・検証・状態管理という地味な部品の積み重ね**だと言われます。
ゴールを満たせないまま回り続けるループを打ち切る上限（回数・予算・時間）、
検証手段そのものが改ざんされていないことの保証（権限分離）、
実行間で壊れない状態ファイル——この3つの作り込みが実用性を決めます。

### ループを支える6つのプリミティブ

エッセイは、この最小ループを実運用に耐える形にする部品を挙げています。
原典での呼び方は「**5つの部品（the five pieces）**」＋別枠の「**6つ目（the sixth thing）**」
としての外部状態で、実践者の間ではこれらをまとめて**6つのプリミティブ**と整理するのが
通例になっています。

| プリミティブ | 役割 | 解消する問題 |
|------|------|------------|
| **Automations（自動化・スケジューリング）** | `/loop`（周期実行）や `/goal`（条件達成まで実行）、cron、CI による繰り返しの起動。ループの心臓 | 人間が毎回起動している |
| **Memory / State（外部状態）** | Markdown ファイルやタスクボードに進捗を永続化。原典が「6つ目」として挙げるもの | モデルは実行間の記憶を持たない |
| **Sub-agents（サブエージェント）** | 実装と検証を別エージェントに分離 | 作った本人の自己採点は甘い |
| **Skills（スキル）** | SKILL.md にプロジェクトの流儀・手順を記述 | 毎周回、約束事をゼロから推測し直す |
| **Worktrees（ワークツリー）** | git worktree で作業コピーを隔離 | 並行するループ同士が衝突する |
| **Plugins / Connectors（コネクタ）** | MCP で Issue トラッカーや PR、チャットに接続 | 仕事の入口と成果の出口がリポジトリの外にある |

### 公式の分類: 4種類のループ

Claude Code の開発チームは、ループを**起動のされ方と止まり方**で4つに分類しています
（[Getting started with loops](https://claude.com/blog/getting-started-with-loops)）。

| 分類 | 起動 | 停止 | 向いている仕事 |
|------|------|------|--------------|
| ターン型 | 人間のプロンプト | モデルが完了と判断したら | 短い単発の作業（通常の対話） |
| ゴール型（`/goal`） | 人間が条件を設定 | 検証可能な条件の達成、または上限ターン数 | 成功が機械判定できる作業 |
| 時間型（`/loop`, `/schedule`） | 一定間隔 | キャンセル、または仕事が尽きたら | 定期作業・外部システムの監視 |
| プロアクティブ型 | イベントやスケジュール（人間は不在） | タスクごとに条件達成で終了、ルーチンは無効化まで継続 | バグトリアージ・依存更新など定型の継続業務 |

本ハンズオンの Step 1 はターン型に検証を埋め込んだもの、Step 4 は時間型に
終了条件を与えたもの（実質ゴール型寄り）に当たります。

### 代表的なループの一日

エッセイが描く運用例はこうです。

1. 朝、スケジュールされた自動実行が CI の失敗と未対応 Issue をトリアージし、状態ファイルに書き出す
2. 隔離された worktree でサブエージェントが起動。1つは修正を実装し、別の1つが仕様とテストで検証する
3. コネクタ経由で PR が開かれ、チケットが更新される
4. 自動で解決できなかったものだけが**人間の受信箱**に届く

人間はループの中にいません。ループの**外**で、設計と監督とトリアージをしています。

## プロンプトエンジニアリングと何が違うのか

一番の違いは**レバレッジの向き**です。良いプロンプトは1回の出力を良くしますが、
良いループは**回るたびに**仕事を進めます。設計の質が結果に複利で効きます。

ただしエッセイは、このレバレッジが**両刃**であることを強調しています。
同じループでも、深く理解したエンジニアが運用すれば生産性の増幅装置になり、
考えることを放棄した人間が運用すれば、誤りの増幅装置になります。

## 段階的自律: L1 → L2 → L3

6つのプリミティブが「ループをどう組むか」の答えだとすれば、
「組んだループにどこまで任せるか」の答えが**段階的自律**です。
実践者の間で定石になっているのは、権限を3段階で広げていくロールアウトです。

| レベル | 任せる範囲 | 人間の関与 |
|--------|----------|----------|
| **L1: 報告のみ** | 分析してレポートを書くだけ。コードに触らない | 報告を読み、次の指示を決める |
| **L2: 補助修正** | 修正案の作成・PR の下書きまで | マージ判定（ゲート承認） |
| **L3: 完全自律** | 実装からマージ・記録まで一気通貫 | 例外だけが届く受信箱のトリアージ |

各レベルで十分な実績（検証・レビュー・停止条件が機能している証拠）を確認してから
次へ進みます。最初の本番ループは必ず L1 から。

なお、この L1/L2/L3 という枠組み自体は原典のエッセイには登場しません。
原典が繰り返す「検証は最後まで人間の責任」という警告を、実務のロールアウト手順に
落とし込んだものとして実践側で定着した整理です（参考文献の DevelopersIO 記事など）。
本ハンズオンの Step 4 で体験する kakeibo のフルループは、砂場だからこそ許される L3 です。

## 人間に残る3つの責任

エッセイの後半は、楽観論ではなく警告に割かれています。

1. **検証責任（Verification）** — 放置されたループは、放置されたミスを犯す。
   「テストが通った」と「正しい」の間の差分を埋めるのは、最後まで人間の仕事
2. **理解負債（Comprehension debt）** — 理解を伴わない高速な出荷は、
   「動いているが誰も説明できないコード」という負債を積む
3. **認知的明け渡し（Cognitive surrender）** — ループの出力をただ受け入れる姿勢は、
   意図を持ったエンジニアリングの対極にある。最も警戒すべき失敗モード

> Build the loop. But build it like someone who intends to stay the engineer,
> not just the person who presses go.
>
> （ループを作れ。ただし、エンジニアであり続けるつもりの者として作れ。
> 「開始ボタンを押すだけの人」としてではなく）

## このハンズオンとの対応

本リポジトリの各ステップは、上のプリミティブを痛みの順に体験する構成になっています。

| プリミティブ | 本ハンズオンでの実装 | Step |
|------|-------------------|------|
| 検証ループ（すべての基礎） | `npm test` / `lint` / `typecheck` を渡して自己修正させる | 1 |
| Memory / State | `BACKLOG.md` | 2 |
| Sub-agents | `.claude/agents/reviewer.md`（SPEC.md を判断基準に検証） | 3 |
| Automations | `/loop`（＋L1→L2→L3 の段階的自律の心得） | 4 |
| Skills / Worktrees / MCP | [発展編](advanced.md)で紹介 | — |
